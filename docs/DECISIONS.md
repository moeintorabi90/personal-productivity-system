## v1 offline-and-backup technical decisions

These implement D-008 to D-017. They are the adopted design for Stage 1B; details are in `BACKUP_FORMAT.md`. "Adopted" means the design is settled. Implemented in Stage 1B (branch `feat/stage-1b-offline-backup`, 2026-10-21); detail choices made during implementation are listed in `BACKUP_FORMAT.md`, "Implementation notes (Stage 1B)", and do not change the owner decisions.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-016 | Every user record carries a client UUID, `createdAt`/`updatedAt` (UTC), a **version vector** keyed by device ID, and a **content hash**. Deletions keep **tombstones**. Append-only history records never change after creation. | Lets import tell "same", "older", "newer", and "edited on both sides" apart without a server, so re-import is idempotent and nothing is overwritten silently. The same primitives serve future sync. | Adopted (design, 2026-10-21); implemented in Stage 1B |
| T-017 | Import is preview → confirm → one atomic local transaction. Only new items are added automatically; newer-in-backup items need confirmation; true conflicts and deletions are stored as pending conflicts with both versions and resolved side by side: keep this device's / use the backup's version for every record; "keep both" (copy with a new ID) only for independent record types without links. Linked records keep their ID and the user picks one version, so links and history stay attached. Replaced versions are archived locally for undo. | Safe and understandable; meets "merge, never replace or delete silently"; avoids ambiguous links and history from copies. | Adopted; approved by the owner as D-015 (2026-10-21) |
| T-018 | Backup container: one UTF-8 JSON file (`.json`) with a header (`format`, integer `formatVersion`, `dataSchemaVersion`, `backupId`, source device, `encryption` = `null` or an envelope with key slots), a payload (plaintext object, or `{ ciphertext }` encrypted with AES-256-GCM using the canonical header as AAD), and a SHA-256 integrity hash over the JCS-canonical document without the `integrity` member. Only product record types are included (`sync_probe` excluded). Shared preferences are a singleton with a reserved constant ID; language and theme are device-local and travel only as information (D-017). `contentHash` compares versions of the same ID only. Untrusted-input limits (file ≤ 32 MiB, ≤ 200,000 entries, JSON depth ≤ 32 and ≤ 4,000,000 values enforced by a constant-memory scan before `JSON.parse`, PBKDF2 iterations 600,000–1,000,000 since no older encrypted files exist, exact salt/IV/key lengths) are checked before any heavy work or key derivation. Passwords are NFC-normalized, which does not unify different Persian/Arabic keyboard characters. Readers upgrade older versions step by step and refuse newer ones. Encryption is optional per export and off by default (D-014); an encrypted v1 file has exactly one `password` key slot and no hint field; the `recoveryKey` slot type is reserved for a possible future format version. | Portable across Windows, Android, and iPhone file pickers; inspectable; upgradeable; damage detectable before a password prompt. | Adopted (design, 2026-10-21); implemented in Stage 1B |
| T-019 | The Stage 1 sync API, authentication, PostgreSQL schema, and client sync engine **stay in the repository, frozen and tested, but are not part of v1**: no further work on them, and the v1 UI must not show account/sync screens or the diagnostic "Sync check notes" (`sync_probe`), all hidden behind one build-time feature flag, off by default. `sync_probe` is never part of a backup. When sync is planned after v1, the code is reviewed first and adapted to T-016 (version vectors instead of server revisions); it may need further changes. | Preserves tested work at low cost and keeps the path to sync simple, without building more server infrastructure now. | Adopted; decided by the owner as D-016 (2026-10-21) |

## Stage 2 technical decisions (organization and quick capture, 2026-10-21)

These apply PRODUCT_SPEC "Capture and organization" and DATA_MODEL where the text left details open. They are implementation choices, not owner decisions; the owner may revise them.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-020 | Record types `projects`, `workstreams`, and `taskDefinitions` are ordinary product records (envelope with version vector, content hash, tombstones) and are exported with **`dataSchemaVersion` 2** (`formatVersion` stays 1). Readers accept data schema versions 1 and 2; each type declares the version that introduced it, so a version-1 file containing Stage 2 types is refused as unknown data. Upgrade 1 → 2 is the identity (only types were added). An older app (Stage 1B) refuses a version-2 file with "made by a newer version". | Follows BACKUP_FORMAT "Versioning and upgrades": `dataSchemaVersion` describes record types and fields; no container change. | Adopted (Stage 2) |
| T-021 | The **quick-capture inbox** is the set of task definitions **without a project**. Capture needs only a title; organizing means choosing a project (and optionally a workstream). Tasks and ideas are captured the same way; there is no separate "idea" type yet. | One record type for "unsorted tasks and ideas" keeps links, backup, and conflicts simple; nothing is copied when an item is organized. | Adopted (Stage 2); a separate idea type would be a later product decision |
| T-022 | A **workstream never moves to another project** (`projectId` is immutable). Every version of a workstream on a device and in a backup must agree on it; a file where they differ is refused. A task's workstream must belong to the task's project, and an inbox task has no workstream. These rules are checked by the repository for typed-in data and on import for every version in a file (records, carried conflicts, archived versions), and again when a version becomes active. | DATA_MODEL "A workstream's project must match the task's project". With an immutable workstream project, a task stays consistent whichever task or workstream version a merge keeps. | Adopted (Stage 2) |
| T-023 | **Archive, not delete.** Projects, workstreams, and tasks are archived (`archivedAt`), which is ordinary data: it merges and conflicts like any edit and is reversible. Archiving a project changes nothing linked to it. Stage 2 has no delete action; deletions (tombstones) arrive only through backup conflicts, and deleting an item that others link to stays refused. | "Archived records do not erase history" (ROADMAP Stage 2); keeps later history (sessions, blocks) attached. | Adopted (Stage 2) |
| T-024 | Stage 2 task fields: title, notes, project, workstream, next action, estimate (whole minutes, 1–10,080), archive state. The **`notes` field is the task's descriptive text** in Stage 2 (PRODUCT_SPEC's "description"); there is no separate description field. **Deferred, not implemented:** recurrence and active weekdays (Stage 3, calendar and planning); relevant output metrics (Stage 5, actual execution and outputs); the task **type**, until the owner defines a clear use case and meaningful categories. Adding any of them later is a `dataSchemaVersion` change with an upgrade step. | Stage 2 scope only; avoids fields with no behavior behind them. | Adopted (Stage 2). **Approved by the owner (2026-10-21):** `notes` as the description; `type` deferred until an owner-defined use case and categories exist; recurrence/active weekdays stay in Stage 3 and output metrics in Stage 5. |

## Stage 3 planning decisions (contract, 2026-10-24; implemented and merged into `main`)

The behavior contract is in PRODUCT_SPEC "Stage 3 planning contract"; data in DATA_MODEL "Stage 3 record types and fields"; backup in BACKUP_FORMAT "Data schema version 3". Two kinds of entries:

- **Adopted (derived):** follows directly from D-019 to D-023 and earlier recorded decisions; no new product choice (T-025 to T-028).
- **Approved by the owner (2026-10-24):** product behavior proposed during contract work and then approved by the owner (T-029 to T-036). The approval covers the behavior stated in the "Decision" column. The exact storage encoding (field names, value encodings such as weekday numbers, and validation limits not stated in the decision itself) in DATA_MODEL and BACKUP_FORMAT is a technical implementation choice that serves that behavior; changing it is an engineering change that must not alter the approved behavior.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-025 | **`dataSchemaVersion` 3**, additive only (`formatVersion` stays 1). New optional fields on existing types — task `recurrence`, shared preference `dailyCapacityMinutes` — are **absent** when not used (never `null`), so every existing record keeps its exact data, content hash, and version vector, and no stored record is rewritten. New type `calendarBlocks`. Readers accept versions 1–3 and validate each file against the types **and fields** of its own version (a version-2 file containing `recurrence` is refused). The upgrades 1 → 2 → 3 are the identity. A Stage 2 app refuses a version-3 file as "made by a newer version". | Adding a field with a default value to stored records would change their content hash and turn every unchanged record into a false conflict between updated and not-yet-updated devices. | Adopted (derived from T-020, BACKUP_FORMAT "Versioning") |
| T-026 | **Occurrences are derived, not stored.** For a displayed local date, a recurring task's unscheduled item is computed from the task's recurrence; it is "scheduled" while at least one planned (not cancelled) block exists for that task and occurrence date (D-023), wherever that block is displayed (D-022). Unscheduled items of past dates are **not carried forward** to later dates. | D-019 (no automatic time or moves) and PRODUCT_SPEC principle 5 (a missed plan must not overload the next day); nothing to merge or migrate per occurrence. | Adopted (derived) |
| T-027 | **Planned blocks are plans only** (`calendarBlocks`): no completion or actual-time fields (Stage 5). A block is **cancelled, not deleted** (restorable). Blocks link to a task definition, so they are linked records: conflicts offer keep/use, never "keep both". Editing a task (rename, move, recurrence change, archive) never changes existing blocks. | DATA_MODEL "Planning versus actual"; T-023 (archive, not delete); D-015. | Adopted (derived) |
| T-028 | **Calendar needs an explicit time zone.** While the shared time zone is not set, calendar views, Today, and scheduling show a prompt to set it (the device's zone may be offered as a one-tap suggestion, never applied silently) and write no planning data. | D-020 ("explicitly configured time zone") and PRODUCT_SPEC "Browser timezone may be suggested but is not silently imposed". | Adopted (derived) |
| T-029 | **Recurrence:** weekly recurrence on selected weekdays only (1–7 distinct weekdays); a required **start date**, defaulting to the current local date (configured time zone) when recurrence is enabled; an optional **inclusive** end date. No "every N weeks", monthly, or yearly patterns in Stage 3. | Needed so past dates do not suddenly show items, and to bound the data shape. Stored as `{ kind: "weekdays", weekdays, startDate, endDate }` with weekdays 0 = Sunday … 6 = Saturday (technical encoding, DATA_MODEL); changing the shape later needs another `dataSchemaVersion`. | **Approved by the owner (2026-10-24)** |
| T-030 | **Block time model.** *(a)* A block stores fixed UTC instants (`startsAt`, `endsAt`); all views show blocks in the **currently configured** zone; changing the configured zone (e.g. when traveling) modifies no block (instants and `occurrenceDate` unchanged), so a block keeps its absolute time, may appear at another local time or date, and still schedules its original occurrence (D-022). *(b)* The block also stores the IANA time zone used when planning it (`timeZone`) and its local date in that zone (`localDate`). A wall time that does not exist (daylight-saving gap) is **refused** with a message (never shifted silently); for an ambiguous wall time (clocks going back) the **earlier** of the two instants is used and its offset is shown. | Required for DST-safe, unambiguous plans; the alternative ("floating" local times that follow the traveler) is a different product behavior. | **Approved by the owner (2026-10-24):** (a) as D-022; (b) approved with T-029 to T-036. |
| T-031 | **Capacity:** one shared daily capacity in whole minutes (1–1,440), applying equally to every day, **unset by default** (no warnings until the user sets it; Today and Settings invite setting it). Planned time of a local date = sum of the durations of its planned blocks within that date (cancelled excluded; overlapping blocks each counted). An over-capacity **warning** when planned block time exceeds capacity; if it does not, but planned time plus the estimates of that date's unscheduled items would, a softer **notice**. Items without an estimate are not counted in the notice and are identified as having no estimate. No per-weekday capacity or days-off settings in Stage 3. | D-021 leaves the value and shape open; inventing a default number would impose an unrequested assumption. Stored as the shared preference `dailyCapacityMinutes` (DATA_MODEL). | **Approved by the owner (2026-10-24)** |
| T-032 | **Quick add** from a title creates a new inbox task (no project) and its planned block **in one transaction**; the user may instead select an existing task. Every block therefore references a task definition. | DATA_MODEL "CalendarBlock … relationship IDs"; keeps later sessions (Stage 5) attached to a task. | **Approved by the owner (2026-10-24)** |
| T-033 | **Scheduling an occurrence:** the form pre-fills the occurrence date and, when the task has an estimate, the estimate as duration; the **start time is always entered by the user**. The user may place the block on a different date from the occurrence date. One occurrence may have several blocks; D-023 remains the rule: the occurrence is scheduled while at least one linked block is planned, and cancelling the last planned block makes it unscheduled. | D-019 forbids automatic times, not pre-filled dates/durations. | **Approved by the owner (2026-10-24)** |
| T-034 | **No skip/dismiss action in Stage 3.** An unscheduled occurrence stays on its own date and is never carried forward; it disappears only when scheduled, when the task's recurrence no longer covers that date, or when the task is archived. | Avoids a new per-occurrence record type before a need is shown. | **Approved by the owner (2026-10-24)** |
| T-035 | **Views by display calendar:** the week view always starts on the configured week start; month boundaries follow the selected display calendar — Gregorian months for "Gregorian", Jalali months for "Jalali", and Gregorian months with Jalali day labels for "Both". Stored dates remain ISO Gregorian (`YYYY-MM-DD`). | D-020 makes Jalali a display choice; month boundaries are a presentation question. | **Approved by the owner (2026-10-24)** |
| T-036 | **Block snapshots:** each block stores a snapshot (task title, project and workstream IDs and names) taken when it is created and refreshed when the **block itself** is edited — not merely because a task, project, or workstream name later changes. Calendar views show the task's **current** title; the snapshot is used when the task is unavailable on that device and for historical context (reviews, sessions in later stages). | DATA_MODEL "historical snapshots"; current names avoid stale titles in upcoming plans. | **Approved by the owner (2026-10-24)** |

### Prisma 7 versus plain SQL + `pg` (checked 2026-10-20)

| Criterion | Prisma 7.10.1 (latest stable; `latest` tag is 8.0.0-rc.23) | Plain SQL + `pg` 8.23 |
|---|---|---|
| Install footprint | `prisma` CLI ~42 MB unpacked plus `@prisma/engines`, `@prisma/dev`, `@prisma/studio-core`, `mysql2`; `@prisma/client` ~74 MB unpacked | `pg` and its small dependencies (well under 1 MB) |
| PGlite for lightweight dev/test | Runtime only through the community `pglite-prisma-adapter` (built against driver utils 7.2.0, version skew); Prisma Migrate needs a database server connection (`prisma dev` adds its own local server) | Same SQL runs directly on PGlite in-process |
| Real PostgreSQL | First-class via `@prisma/adapter-pg` | First-class |
| Migrations | Generated, reviewable SQL; strong drift detection | Hand-written SQL; simple runner; no drift detection |
| Type safety | Generated types | Manual row types plus Zod validation at boundaries |
| Fit for sync rules (row locks, append-only log, revision checks) | Often needs raw SQL anyway | Direct |

Conclusion: for Stage 1 on this machine, plain SQL + `pg` is smaller, runs unchanged on PGlite and PostgreSQL, and keeps the sync transaction logic explicit. Revisit Prisma (or a lighter query builder) if Stage 2+ query volume makes hand-written SQL error-prone.
