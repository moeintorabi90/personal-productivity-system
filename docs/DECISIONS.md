## v1 offline-and-backup technical decisions

These implement D-008 to D-017. They are the adopted design for Stage 1B; details are in `BACKUP_FORMAT.md`. "Adopted" means the design is settled. Implemented in Stage 1B (branch `feat/stage-1b-offline-backup`, 2026-10-21); detail choices made during implementation are listed in `BACKUP_FORMAT.md`, "Implementation notes (Stage 1B)", and do not change the owner decisions.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-016 | Every user record carries a client UUID, `createdAt`/`updatedAt` (UTC), a **version vector** keyed by device ID, and a **content hash**. Deletions keep **tombstones**. Append-only history records never change after creation. | Lets import tell "same", "older", "newer", and "edited on both sides" apart without a server, so re-import is idempotent and nothing is overwritten silently. The same primitives serve future sync. | Adopted (design, 2026-10-21); implemented in Stage 1B |
| T-017 | Import is preview → confirm → one atomic local transaction. Only new items are added automatically; newer-in-backup items need confirmation; true conflicts and deletions are stored as pending conflicts with both versions and resolved side by side: keep this device's / use the backup's version for every record; "keep both" (copy with a new ID) only for independent record types without links. Linked records keep their ID and the user picks one version, so links and history stay attached. Replaced versions are archived locally for undo. | Safe and understandable; meets "merge, never replace or delete silently"; avoids ambiguous links and history from copies. | Adopted; approved by the owner as D-015 (2026-10-21) |
| T-018 | Backup container: one UTF-8 JSON file (`.json`) with a header (`format`, integer `formatVersion`, `dataSchemaVersion`, `backupId`, source device, `encryption` = `null` or an envelope with key slots), a payload (plaintext object, or `{ ciphertext }` encrypted with AES-256-GCM using the canonical header as AAD), and a SHA-256 integrity hash over the JCS-canonical document without the `integrity` member. Only product record types are included (`sync_probe` excluded). Shared preferences are a singleton with a reserved constant ID; language and theme are device-local and travel only as information (D-017). `contentHash` compares versions of the same ID only. Untrusted-input limits (file ≤ 32 MiB, ≤ 200,000 entries, JSON depth ≤ 32 and ≤ 4,000,000 values enforced by a constant-memory scan before `JSON.parse`, PBKDF2 iterations 600,000–1,000,000 since no older encrypted files exist, exact salt/IV/key lengths) are checked before any heavy work or key derivation. Passwords are NFC-normalized, which does not unify different Persian/Arabic keyboard characters. Readers upgrade older versions step by step and refuse newer ones. Encryption is optional per export and off by default (D-014); an encrypted v1 file has exactly one `password` key slot and no hint field; the `recoveryKey` slot type is reserved for a possible future format version. | Portable across Windows, Android, and iPhone file pickers; inspectable; upgradeable; damage detectable before a password prompt. | Adopted (design, 2026-10-21); implemented in Stage 1B |
| T-019 | The Stage 1 sync API, authentication, PostgreSQL schema, and client sync engine **stay in the repository, frozen and tested, but are not part of v1**: no further work on them, and the v1 UI must not show account/sync screens or the diagnostic "Sync check notes" (`sync_probe`), all hidden behind one build-time feature flag, off by default. `sync_probe` is never part of a backup. When sync is planned after v1, the code is reviewed first and adapted to T-016 (version vectors instead of server revisions); it may need further changes. | Preserves tested work at low cost and keeps the path to sync simple, without building more server infrastructure now. | Adopted; decided by the owner as D-016 (2026-10-21) |

These apply PRODUCT_SPEC "Capture and organization" and DATA_MODEL where the text left details open. They are implementation choices, not owner decisions; the owner may revise them.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-020 | Record types `projects`, `workstreams`, and `taskDefinitions` are ordinary product records (envelope with version vector, content hash, tombstones) and are exported with **`dataSchemaVersion` 2** (`formatVersion` stays 1). Readers accept data schema versions 1 and 2; each type declares the version that introduced it, so a version-1 file containing Stage 2 types is refused as unknown data. Upgrade 1 → 2 is the identity (only types were added). An older app (Stage 1B) refuses a version-2 file with "made by a newer version". | Follows BACKUP_FORMAT "Versioning and upgrades": `dataSchemaVersion` describes record types and fields; no container change. | Adopted (Stage 2) |
| T-021 | The **quick-capture inbox** is the set of task definitions **without a project**. Capture needs only a title; organizing means choosing a project (and optionally a workstream). | T-022 | A **workstream never moves to another project** (`projectId` is immutable). Every version of a workstream on a device and in a backup must agree on it; a file where they differ is refused. A task's workstream must belong to the task's project, and an inbox task has no workstream. These rules are checked by the repository for typed-in data and on import for every version in a file (records, carried conflicts, archived versions), and again when a version becomes active. | DATA_MODEL "A workstream's project must match the task's project". Archiving a project changes nothing linked to it. Stage 2 has no delete action; deletions (tombstones) arrive only through backup conflicts, and deleting an item that others link to stays refused. | "Archived records do not erase history" (ROADMAP Stage 2); keeps later history (sessions, blocks) attached. | Adopted (Stage 2) |
| T-024 | Stage 2 task fields: title, notes, project, workstream, next action, estimate (whole minutes, 1–10,080), archive state. ## Stage 3 planning decisions (contract, 2026-10-24; implemented and merged into `main`)

The behavior contract is in PRODUCT_SPEC "Stage 3 planning contract"; data in DATA_MODEL "Stage 3 record types and fields"; backup in BACKUP_FORMAT "Data schema version 3". Two kinds of entries:

- **Adopted (derived):** follows directly from D-019 to D-023 and earlier recorded decisions; no new product choice (T-025 to T-028).
- **Approved by the owner (2026-10-24):** product behavior proposed during contract work and then approved by the owner (T-029 to T-036). The approval covers the behavior stated in the "Decision" column. The exact storage encoding (field names, value encodings such as weekday numbers, and validation limits not stated in the decision itself) in DATA_MODEL and BACKUP_FORMAT is a technical implementation choice that serves that behavior; changing it is an engineering change that must not alter the approved behavior.

| ID | Decision | Reason | Status |
|---|---|---|---|
| T-025 | **`dataSchemaVersion` 3**, additive only (`formatVersion` stays 1). New optional fields on existing types — task `recurrence`, shared preference `dailyCapacityMinutes` — are **absent** when not used (never `null`), so every existing record keeps its exact data, content hash, and version vector, and no stored record is rewritten. New type `calendarBlocks`. Readers accept versions 1–3 and validate each file against the types **and fields** of its own version (a version-2 file containing `recurrence` is refused). The upgrades 1 → 2 → 3 are the identity. A Stage 2 app refuses a version-3 file as "made by a newer version". | Adding a field with a default value to stored records would change their content hash and turn every unchanged record into a false conflict between updated and not-yet-updated devices. | Adopted (derived from T-020, BACKUP_FORMAT "Versioning") |
| T-026 | **Occurrences are derived, not stored.** For a displayed local date, a recurring task's unscheduled item is computed from the task's recurrence; it is "scheduled" while at least one planned (not cancelled) block exists for that task and occurrence date (D-023), wherever that block is displayed (D-022). Unscheduled items of past dates are **not carried forward** to later dates. | D-019 (no automatic time or moves) and PRODUCT_SPEC principle 5 (a missed plan must not overload the next day); nothing to merge or migrate per occurrence. | Adopted (derived) |
| T-027 | **Planned blocks are plans only** (`calendarBlocks`): no completion or actual-time fields (Stage 5). A block is **cancelled, not deleted** (restorable). Blocks link to a task definition, so they are linked records: conflicts offer keep/use, never "keep both". Editing a task (rename, move, recurrence change, archive) never changes existing blocks. | DATA_MODEL "Planning versus actual"; T-023 (archive, not delete); D-015. | Adopted (derived) |
| T-028 | **Calendar needs an explicit time zone.** While the shared time zone is not set, calendar views, Today, and scheduling show a prompt to set it (the device's zone may be offered as a one-tap suggestion, never applied silently) and write no planning data. | D-020 ("explicitly configured time zone") and PRODUCT_SPEC "Browser timezone may be suggested but is not silently imposed". | Adopted (derived) |
| T-029 | **Recurrence:** weekly recurrence on selected weekdays only (1–7 distinct weekdays); a required **start date**, defaulting to the current local date (configured time zone) when recurrence is enabled; an optional **inclusive** end date. No "every N weeks", monthly, or yearly patterns in Stage 3. | Needed so past dates do not suddenly show items, and to bound the data shape. Stored as `{ kind: "weekdays", weekdays, startDate, endDate }` with weekdays 0 = Sunday … 6 = Saturday (technical encoding, DATA_MODEL); changing the shape later needs another `dataSchemaVersion`. | **Approved by the owner (2026-10-24)** |
| T-030 | **Block time model.** *(a)* A block stores fixed UTC instants (`startsAt`, `endsAt`); all views show blocks in the **currently configured** zone; changing the configured zone (e.g. when traveling) modifies no block (instants and `occurrenceDate` unchanged), so a block keeps its absolute time, may appear at another local time or date, and still schedules its original occurrence (D-022). *(b)* The block also stores the IANA time zone used when planning it (`timeZone`) and its local date in that zone (`localDate`). A wall time that does not exist (daylight-saving gap) is **refused** with a message (never shifted silently); for an ambiguous wall time (clocks going back) the **earlier** of the two instants is used and its offset is shown. | Required for DST-safe, unambiguous plans; the alternative ("floating" local times that follow the traveler) is a different product behavior. | **Approved by the owner (2026-10-24):** (a) as D-022; (b) approved with T-029 to T-036. |
| T-031 | **Capacity:** one shared daily capacity in whole minutes (1–1,440), applying equally to every day, **unset by default** (no warnings until the user sets it; Today and Settings invite setting it). Planned time of a local date = sum of the durations of its planned blocks within that date (cancelled excluded; overlapping blocks each counted). An over-capacity **warning** when planned block time exceeds capacity; if it does not, but planned time plus the estimates of that date's unscheduled items would, a softer **notice**. Items without an estimate are not counted in the notice and are identified as having no estimate. No per-weekday capacity or days-off settings in Stage 3. | D-021 leaves the value and shape open; inventing a default number would impose an unrequested assumption. Stored as the shared preference `dailyCapacityMinutes` (DATA_MODEL). | **Approved by the owner (2026-10-24)** |
| T-032 | **Quick add** from a title creates a new inbox task (no project) and its planned block **in one transaction**; the user may instead select an existing task. Every block therefore references a task definition. | DATA_MODEL "CalendarBlock … relationship IDs"; keeps later sessions (Stage 5) attached to a task. | **Approved by the owner (2026-10-24)** |
| T-033 | **Scheduling an occurrence:** the form pre-fills the occurrence date and, when the task has an estimate, the estimate as duration; the **start time is always entered by the user**. The user may place the block on a different date from the occurrence date. One occurrence may have several blocks; D-023 remains the rule: the occurrence is scheduled while at least one linked block is planned, and cancelling the last planned block makes it unscheduled. | D-019 forbids automatic times, not pre-filled dates/durations. | **Approved by the owner (2026-10-24)** |
| T-034 | **No skip/dismiss action in Stage 3.** An unscheduled occurrence stays on its own date and is never carried forward; it disappears only when scheduled, when the task's recurrence no longer covers that date, or when the task is archived. | Avoids a new per-occurrence record type before a need is shown. | **Approved by the owner (2026-10-24)** |

| T-036 | **Block snapshots:** each block stores a snapshot (task title, project and workstream IDs and names) taken when it is created and refreshed when the **block itself** is edited — not merely because a task, project, or workstream name later changes. **Derived technical choices** (follow from the decisions above and the repository's rules; **not owner decisions**; may be revised in technical review without changing the approved behavior):

- **`dataSchemaVersion` 8:** new record types and fields need a new data version (BACKUP_FORMAT "Versioning and upgrades"; current version 7). The whole Stage 6 data goes in one step, as in versions 3 and 6. Earlier apps refuse version 8 as newer; older files keep importing, and every format change ships with a test that imports the previous version's stored sample.
- **Stage of the app-use streak:** because the Stage 6 main dashboard shows it by default (T-202), it is built in Stage 6 instead of Stage 8.
- **Workdays:** days of the week, as T-053 describes them. An **opportunity** is a selected weekday from the goal's start date until its deadline, if any, outside paused and archived periods and before completion. It is missed only after its local day ends (as before). A goal without workdays has no opportunities, so no streak.
- **Which plan applies:** a plan change takes effect from its local date in the configured zone. Goals without history are treated as having had their current target, deadline, workdays, and cap from their start date; the unknown past is not reconstructed. Weekly plans before version 8 are not reconstructed either (data design below).
- **Weekly allocation formula (T-206, T-208):** the owner chose no formula. Allocations exist only for a goal with selected workdays and a deadline (T-180); without them, manual amounts stay inactive (T-213), and when they return, the amounts that fit become active again (T-215). The amount to share is the target, minus actual progress through closed weeks, minus the manual amounts of open weeks. It is shared in proportion to each automatic week's selected workdays within the goal's dates, so 600 over four equal weeks gives 150 each, and 100 over weeks with 2, 5, and 3 workdays gives 20, 50, and 30. A week with no selected workdays gets no automatic amount and cannot be given a new manual amount; a manual amount it already has stays correctable (T-212). A manual amount is a whole number of zero or more in the goal's measure (T-051, T-085).
- **Open and closed weeks:** weeks follow the configured week start (D-020) in the configured time zone, so a goal's first and last weeks may be partial. A week closes when its last local day ends. "Future weeks" in T-208 means weeks not yet closed, including the current one; only these can be edited. Automatic amounts change when a week closes, when the plan is edited, and when a closed week's actual records are corrected; work recorded in the current week does not change them. All work recorded in a week counts toward it, also on unselected days.
- **Rounding:** calculations keep exact values, and automatic amounts are never rounded in the calculation. Displayed amounts show at most two decimals, so 400 over three weeks shows 133.33 each. Whether a mismatch exists is decided from whole numbers (target, actual, manual amounts), so rounding cannot cause or hide one.
- **When a mismatch exists (T-207):** while a goal has allocations, when the amount to share is negative, or when it is above zero and no automatic week can take it. The discrepancy shown is the absolute value of that amount. With no manual amounts, a goal already past its target has automatic amounts of zero and no mismatch. During a mismatch, automatic weeks show no amount. Manual weeks can switch back to automatic at any time, not only during a mismatch. A manual amount that T-211, T-212, or T-215 keeps outside the current weeks, or on a week with no selected workday, is itself a mismatch, so T-207, T-209, and T-210 apply; it is shown separately and is not part of the amount to share. Once its week is closed, it stays only as a historical warning and no longer stops targets (T-219).
- **Moves (T-218, T-220):** the destination can only be an open week, current or future, since a closed week cannot be edited (T-206, T-208). Moving from a closed week never rewrites that week's fixed historical plan (T-208). A mismatch is never resolved automatically, and a move happens only by the owner's explicit action (T-207, T-218).
- **Cap during a mismatch:** the daily cap gives no displayed target, but maximum projected attainment does not depend on the allocation and stays visible (T-183). The unreachable-goal warning is shown when that attainment is below the target, next to the separate mismatch warning (T-221); the same test applies when allocations match (T-222).
- **After the deadline or completion:** no week is open, so there are no allocations and no mismatch; T-187 applies, or the goal is complete.
- **Daily target:** (the week's allocation − the amount recorded earlier that week) ÷ selected workdays remaining in the week, counting today if it is one, so it stays stable during the day; never below zero, and a target of zero counts as met. Under a cap: the smaller of that and the cap. A fractional target is met when the whole-number actual reaches it. **Weekly target:** the week's allocation, with the week's progress as a percentage; all work recorded in the week counts, also on unselected days. **Monthly target:** each week's allocation split by its selected workdays, adding the shares that fall in the month of the display calendar, so a week that crosses a month boundary counts in both; the month's progress is a percentage. During a mismatch no monthly target is shown (T-209). **Maximum projected attainment:** current progress + cap × remaining workdays. A daily cap is a whole number in the goal's measure, like its target (T-051, T-085).
- **Daily pace streak:** uses the same opportunities as the consistency streak and is derived rather than stored; its longest value is calculated from the current, corrected history (T-216). Opportunities without a daily target, during a mismatch or without a recorded plan, are skipped (T-210, T-226). Both streaks may appear on the goal page and as cards.
- **Plan used for comparison:** an edit is "before the scheduled start" when it is made before the start the block had just before that edit. Cancelling follows the same rule. Blocks without a stored baseline use their current times; the unknown past is not reconstructed.
- **Local-day aggregation:** a session's active time is split at local midnight in the configured zone, for comparisons and rates; the record is unchanged.
- **Estimate capture:** a new record per task occurrence (one-off tasks: no occurrence date), whose ID is derived from the task and date, as for completions (T-119). A task with no estimate captures none. Occurrences planned or started before version 8 have no capture and show "no data"; the current estimate is never back-filled.
- **Session occurrence:** an optional session field; a session started from a block takes the block's occurrence date. A recurring-task session without one counts in task totals but not in per-occurrence accuracy, and is shown as unassigned. **Reopening** a completion removes it from accuracy until it is completed again.
- **Percent difference:** (actual − estimate) ÷ estimate.
- **Initial output unit suggestions:** minute, hour, page, word, chapter, lesson, article, exercise, question, flashcard, session, kilometer, and rep, in English and Persian. The list is a derived implementation choice, **not an owner-approved list**, and suggestions only fill the definition form (T-050, T-165 are unchanged).

- **Data design for weekly allocations (technical review of 2026-11-02; derived, not owner decisions):**
  - **Manual allocations:** one `goalWeekAllocations` record per goal and week, with an ID derived from the goal and `weekStart` (as for completions, T-119). `weekStart` is the first day of the calendar week under the week start configured when the record is created; for a goal's partial first week it is still the calendar week's first day, so moving the goal's start date or deadline never changes it. `goalId` and `weekStart` never change; the record is never rewritten to another week and is not refused on import for not matching the current week start (T-211, T-212). Its `revisions` list holds `{ from, amount }` entries with the local date each value took effect; `amount` is a whole number of zero or more, or `null`, which means **"no manual amount, so automatic"**. A change on the same local date replaces that day's entry; a later change appends one, so the value before and after a move or edit stays visible with its date (T-182, T-218, T-224). Deleting the record is never used for "automatic", because a deleted ID cannot be created again.
  - **Effective plan of each week:** one `goalWeekPlans` record per goal and week, with an ID derived from the goal and `weekStart`, holding one entry per effective date ("segment" below), whose content is `{ state, allocation, source }`, where `state` is allocated, mismatch, inactive, or none, `allocation` is an exact fraction `{ num, den }` (or `null` unless allocated), and `source` is manual or automatic; how an entry keeps the segments of several devices is under "Segment merge". The first device to run the app during a week writes the first segment, from the local date it is written; it is never backdated (T-225). A change that alters the current week's allocation (a goal-plan edit, an allocation edit or move, removing or restoring the deadline or workdays, or a correction of a closed week's actual output) appends a segment from that local date, in the same transaction as the change. Future weeks get a record only when they start. The app never computes or appends a segment for a closed week by itself (T-208). Only two things write to a closed week's record: an import that adds another device's entries (T-227), and the owner's explicit decision or change of choice between recorded versions (T-223, T-227; "Segment merge").
  - **Which segment applies:** on each day, the segment with the latest `from` on or before that day, among the goal's week records whose seven days include it. After a change of week start, the first segment of the newly keyed week starts on the day it is written, so earlier days keep the earlier week's plan (T-217). Daily targets and both streaks are recalculated from that segment and the current actual records, so corrections change past results but never the segment (T-214, T-216, T-217). When the owner changes the choice for a date, the segment in effect from that date changes, and the past daily targets, the daily pace streak, and its longest value are recalculated from it in the same way.
  - **Days without a recorded plan (T-225):** days before a goal's first segment, the days of a week in which the app was not run, and weeks before version 8 have no record and show "no data" for allocation, daily target, and pace; no record is written for them later and no historical plan is guessed. The amount to share for later weeks still uses the actual output of every closed week (T-208). The daily pace streak starts on the first day with a recorded plan in effect. A day without a plan neither adds to nor breaks the streak; if a record for that week made on another device arrives by import, its segments apply and the streak is recalculated (T-226). Recording actual output never creates a plan.
  - **State of manual allocations:** active, out of range, or inactive is calculated by a pure function and never stored, so nothing is deleted or moved (T-211 to T-213). When the deadline or workdays return, the allocations that fit are active again and the others show the mismatch (T-215). A closed week's out-of-range allocation is only a historical warning (T-219).
  - **Conflicts (T-223, T-227):** neither type is append-only. Identical content from two devices has the same hash and is "already here", and different weeks are different records that merge without conflict. For the same week, `goalWeekAllocations` versions that differ are an ordinary conflict in which the owner chooses the version to keep. `goalWeekPlans` versions are merged by date instead, as "Segment merge" describes. Nothing is chosen by time or age. Merging can add another device's entries to a closed week's record but never changes what this device wrote there (T-208); only the owner's own decision replaces this device's entry.
  - **Segment merge (T-227 to T-229):** each effective date of a `goalWeekPlans` record (the record's segments, `goalWeekPlans.segments` in T-227) holds one **entry per device**, not a single segment.
    - **Entry:** `{ device, seq, segment, seen }`. `segment` is what that device last wrote or chose for the date; `seq` is a counter that only that device raises, by one each time it writes or decides that date; `seen` maps each other device to the highest `seq` of its entry for that date that this device had when it wrote this one. A device has exactly one entry per date: a new write or decision replaces its earlier entry, so one device can never hold two positions at once.
    - **Merge:** per device, the entry with the higher `seq` is kept; the lower one is gone for good, so an older backup of a device can never bring back its earlier choice or remove its later one. The same device and `seq` with different content is an integrity issue: it is shown as such and nothing changes. Because the merge only takes a per-device maximum, its result does not depend on the order or the number of times backups arrive.
    - **Live entries and candidates:** an entry of device D is **covered** when another device's entry has `seen[D]` equal to or higher than its `seq`, meaning that device saw it and then took its own position. The candidates of a date are the distinct segments of the entries not covered, compared by exact equality of their canonical JSON (JCS); a hash may be used to find a match, but a hash match alone never merges different content.
    - **Options kept for a later change of mind:** each date also keeps `options`, a list of the segments the owner has chosen between for that date. *(Revised 2026-11-04 after Codex's review; derived: the earlier rule, "whenever a merge or a decision leaves more than one candidate, those candidates are added", made the list depend on the order of imports, because which candidates met in an intermediate merge depends on that order: A writing x and B writing y unseen, and C writing z after seeing only A, gave `options` x, y, z after (A+B)+C but y, z after (A+C)+B, with identical entries.)* Only an owner decision adds to it: the segments shown to choose between (the candidates, all entries' segments for an inconsistent date, or the segment applying before a change of choice) and the chosen one. Merges and the app's own plan writes add nothing; the merge takes the union, keeps each segment once by exact canonical equality, and sorts the list by canonical JSON. With the per-device maximum of entries, the merge is commutative, associative, and idempotent, so devices that have exchanged the same backups hold the same record and the same list, whatever the order or repeats. Conflict candidates are still shown and chosen from the live entries (T-223, T-227), and nothing is removed from `options`. `options` has no count limit (the owner's choice of 2026-11-04, below); the weekly plan record as a whole stays within the per-record limit instead. `options` is history only: it never decides what applies, and a segment in it becomes current only through a new decision (below). So importing an old backup can add a segment to `options`, which is harmless, but can never make that segment current.
    - **What applies on a day:** one candidate applies on every device, so devices that hold the same segment, or whose later entries saw and replaced the others, have converged. Several candidates are a conflict for the owner: this device's own entry applies if it is still a candidate (T-227); a device with no candidate entry of its own shows "no data" for that date until the owner decides (T-228), and the pace streak follows T-226 meanwhile. Nothing is chosen by time, age, or whichever device wrote last.
    - **Deciding a date:** the owner's choice replaces this device's entry for that date with `{ seq + 1, chosen segment, seen = every entry shown }`: `seq` is one more than this device's own previous `seq` for that date (1 if it had none), and `seen` holds, for each other device, the `seq` of its entry for that date currently on this device. That covers every entry the owner saw, so the date is settled here and on any device that imports it.
    - **Changing one's mind after a decision:** a settled date whose `options` hold more than one segment shows a "Change choice" action in the goal's weekly plan view; while the date is undecided, the same choice is in the conflict list. It lists the `options`, marks the one now applying, and after the owner picks another and confirms, records a new decision exactly as above, with the chosen segment taken from `options`. It also writes a history event (T-237). Its higher `seq` replaces this device's earlier decision, and its `seen` covers every entry on this device, so it is the only live entry until another device writes without having seen it. Only segments already in `options` can be chosen, so this changes which recorded plan applies but never creates a new plan for a past date. The action is offered for closed weeks too (derived; confirmed by the owner on 2026-11-03), since it only chooses between recorded versions (T-223, T-227) and never computes a plan; the app itself still never recomputes a closed week (T-208). After a change, the days from that date on use the newly chosen segment, and their daily targets, the daily pace streak, and its longest value are recalculated (T-214, T-216, T-217). No other date and no other segment is touched. An entry another device writes later without having seen this decision stays live, and the date becomes a conflict again; one written after seeing it covers it, as any later edit covers an earlier version.
    - **Choice history (T-237):** every owner decision or change of choice for a date also writes, in the same transaction, one `goalWeekPlanChoices` record. It is append-only, with `goalId`, `weekStart`, `from` (the date), `device` and `deviceName` (the deciding device and its name then), `seq` (the counter of the entry this decision wrote), `previous` (the segment that applied here for that date just before, or `null` when nothing did, because the date was undecided or had no data), `chosen` (the segment chosen), `seen` (a copy of the entry's `seen`), and `recordedAt` (this device's clock). Its ID is derived from the goal, `weekStart`, `from`, `device`, and `seq`, as completion IDs are (T-119), so the same decision is always one record. Merges, imports, and the app's own plan writes never create events.
    - **Merging history:** being append-only, events from two devices combine by union through the ordinary import: an event already here is "already here", so importing the same backup again adds nothing, and an older backup only holds older events, so it can add missing ones but never remove or reorder any. The same ID with different content is the existing append-only integrity warning: both versions are shown and nothing changes. Events are new records, so they are imported whether or not "Apply updates" is chosen (D-015); an event never changes `goalWeekPlans` or which segment applies.
    - **Status of an event (technical completion of T-237):** shown, never stored, and recalculated whenever the history is displayed, from this device's `goalWeekPlans` record for the goal and week and that record's entry for the event's `device` on its `from` date. **Not applied here:** there is no such record, no entry for that device, or the entry's `seq` is lower than the event's, because the plan merge was skipped (T-229) or that plan has not arrived yet. **Current:** the entry's `seq` equals the event's and the entry is live. **Replaced later:** the entry's `seq` is higher than the event's, or the entry is covered by another device's entry, so a later decision or write has taken its place. **Integrity check when the counters are equal:** the event and the entry were written in one transaction, so with the same `seq` the event must match the entry: `chosen` equals the entry's `segment` and `seen` equals the entry's `seen`, both by exact canonical equality, and its goal, week, date, and device are those of the entry. If they do not match, the event is shown as a data-integrity issue instead of "current" or "replaced later", and nothing in the plan or the history is changed. The check is part of computing the status, so it also runs when the plan record arrives after the event. When a plan record or a newer entry arrives later, the status changes on the next display, for example from "not applied here" to "current" or "replaced later"; the event itself is never edited, deleted, or used to apply a plan, and a replaced event stays in the history.
    - **Order of events:** within one device, `seq` gives the exact order. Between devices, an event of device B comes after one of device A when its `seen` for A is equal to or higher than that event's `seq`, meaning B had seen it; otherwise the two are independent, and neither came first in any reliable sense. `recordedAt` comes from each device's own clock, which may be wrong or differ between devices, so it is shown and used only to place independent events near each other in the list, never to decide which choice applies or that one is newer. The history view in "Change choice" lists, for the date, each event's previous and new choice, time, and device, oldest first in that order, and marks independent events as "order not certain".
    - **Import (T-229, D-015):** a plan record that is older or identical is skipped as for any record. A plan record not on this device is new and is imported as any new record, whether or not "Apply updates" is chosen, with any undecided date it carries; T-228 then applies to that date, and dates with a single candidate are used. A plan record already on this device that is newer or concurrent is merged only when "Apply updates" is chosen; otherwise the existing record is not changed, nothing of the incoming one is written, including its conflict state, and it is counted as skipped. A backup with both kinds adds the new records and gates only the merges. The merged record's version merges both version vectors; this device's counter is raised only when the merged data differs from what it had, so importing the same file again, or a file already merged elsewhere, changes nothing. Entries are kept in a fixed order (dates, then device IDs), so two devices that merge the same versions produce the same content and hash.
    - **Preview:** new weekly plans are counted with the other new records; plans already here that would be merged with "Apply updates", and the dates that would then need the owner's decision, have counts of their own; the "Apply updates" option is offered whenever there are any merges. Undecided dates arriving in new records are counted as dates needing a decision. Dates already in conflict here are not counted again.
    - **Storage:** an undecided date, the owner's decisions, and the `options` live inside the record, so they travel in backups and reach a third device with the record. `pendingConflicts`, `replacedVersions`, the carried-conflict format, and `formatVersion` 1 are unchanged; only the proposed version-8 shape of `goalWeekPlans` reflects this. A tombstone for this type is refused, since goals cannot be deleted while linked.
  - **Moves (T-218, T-220, T-224):** one transaction appends a revision to the source (`null`) and to the destination (the moved amount, or the sum, as the owner chose), and a segment if the current week changes. Cancelling writes nothing. No separate move record exists.
- **History fields:** `goals.planHistory` (target, deadline, workdays, and daily cap, with `effectiveFrom`) and `calendarBlocks.comparisonPlan` are fields on the existing records, as in definition revisions (T-111): each is written in the same edit as the change, and a conflict keeps the history of the chosen version, with the other version in the archive. `comparisonPlan` is written only by the first edit after the block's scheduled start and is not changed afterwards (T-179). Weekly allocations are not part of `planHistory`; their history is in the two record types above.
- **Charts:** drawn as SVG by the app's own React components, with no new dependency; each chart has a table alternative for screen readers.
- **Timer and floating view (T-230; derived, not owner decisions):**
  - **Three timers, one view state:** (1) the elapsed time of the open work session, computed from the session's stored start and pauses, as its work time already is (T-092, T-110); (2) the standalone stopwatch (T-231, T-235); (3) the countdown (T-232 to T-234). Each has one state, and nothing ticks in storage. The timer view shows whichever of them the user selects, and the in-app timer and the floating view read that same state and send the same commands to the selected timer only, so they always agree; the floating window never creates a timer of its own, and opening or closing it starts, stops, or resets nothing. Ending a work session from either view still does not complete its task (T-091).
  - **Document Picture-in-Picture:** the floating control is shown only when `documentPictureInPicture` exists in the page; support is decided at run time by the API's presence, never by browser name or version. The window is opened from a user action and renders the app's own timer components. Documented limits (MDN): it needs a secure context (HTTPS); there is at most one per browser tab, and the browser may limit the total; it cannot be navigated; the site cannot set its position; and it never outlives the window that opened it, so closing or leaving the app's tab closes it. For reference only, MDN's browser-compatibility data (checked 2026-11-03) lists the API in desktop Chrome and Edge from version 116, in Opera, and in desktop Firefox from version 151, and not in Safari, on iPhone, or in Android browsers, which therefore show only the in-app timer. No other floating method (such as video Picture-in-Picture or a native helper) is used.
  - **Standalone stopwatch storage (T-231, T-235):** one device-local row in the existing `meta` table (key `stopwatch`): `{ status, accumulatedMs, runningSince }`, where `status` is idle, running, or paused, `accumulatedMs` is the time from earlier runs, and `runningSince` the instant the current run started (`null` unless running). Elapsed time is `accumulatedMs` plus, while running, the current clock minus `runningSince`, so time keeps counting while the app is closed and a paused stopwatch stays as it was. Pausing adds the current run to `accumulatedMs`; resetting returns it to idle. It is not a record: no envelope or version vector, never exported, untouched by imports, and it writes no session, history, or progress.
  - **Countdown storage (T-232 to T-234):** one device-local row in the existing `meta` table (key `countdown`): `{ status, durationMs, endsAt, remainingMs }`, where `status` is idle, running, paused, or expired; `endsAt` is the instant it reaches zero while running, and `remainingMs` the time left while paused. Remaining time is always computed from `endsAt` and the current clock, so time passes while the app is closed and a reopened app shows the remaining time or "expired". The sound setting is another device-local `meta` row (key `timerSound`, on by default). These rows, like the stopwatch's, are not records: they have no envelope or version vector, are not exported, and are untouched by imports, like the device's language and theme (D-017). No `dataSchemaVersion` change and no IndexedDB schema change are needed, since `meta` already exists.
  - **Zero (T-233):** while the app is open, reaching zero sets the state to expired, shows the message, and plays a short tone generated with the Web Audio API (no sound file, no dependency) unless the sound is off; the countdown's own start counts as the user action browsers require before playing audio. If zero passes while the app is closed, reopening shows "expired" without playing the tone late. Nothing calls the session's end or the task's complete commands.
  - **Selected timer (T-236):** one device-local row in the existing `meta` table (key `selectedTimer`), holding `session`, `stopwatch`, or `countdown`, written only when the user selects a timer and read when the app opens; with no row yet, the work-session timer is selected. If `session` is restored but no session is open, the work-session timer view shows its empty state with the usual way to start work, and the selection stays `session` until the user changes it; nothing is started or changed. Like the other timer rows it is not a record, is not exported (export reads only named `meta` keys), and is untouched by imports.
  - **Compact floating view (T-238; derived, 2026-11-04):** the floating window shows the compact view while its own viewport (`innerWidth`, `innerHeight` of the Picture-in-Picture window, read on opening and on its `resize` event) is narrower than 300 or lower than 240 CSS pixels; it opens at 340 by 300, so it starts in the full view. The main window's size plays no part, and the in-app timer always shows the full view. The compact view renders from the same timer state as the full view, so switching remounts no timer and writes nothing; an unsaved countdown length typed in the floating window's full view is a draft of that view and is not kept across the switch. Each view's length fields follow the countdown's stored `durationMs` whenever it changes, so a length started in one view appears in the other's fields; an unsaved draft stays in its own view. Start in the compact view uses the countdown's last set length (`durationMs`). Ending a session, Reset, and the length fields are only in the full view.
  - **Countdown length fields (T-239; derived, 2026-11-04):** the fields are a draft shown while the countdown is ready to start (idle or expired), filled from the stored `durationMs`; Start stores their sum in `durationMs` (whole seconds), so a running or paused countdown, which shows no fields, is never changed by them. An empty field counts as 0, and Persian and Arabic-Indic digits are accepted. Errors, in this order: not a whole number, minutes or seconds above 59, a zero length, more than 24 hours. Nothing in storage changes: the countdown row keeps its shape.
  - **No new dependency, no new backup data, and no `dataSchemaVersion`, `formatVersion`, or IndexedDB schema change** for the stopwatch, the countdown, the selected timer, or the floating view; the existing `meta` table holds their device-local rows, and export reads only named `meta` keys, so new keys are not exported.

**Unresolved technical choices:**

- **The 64-option limit of a weekly plan date (Codex review, 2026-11-04). *Resolved by the owner on 2026-11-04: the first option below. The count limit is removed and the per-record size limit is applied with an explicit, tested check; see "Per-record size of weekly plans" under the implementation choices.* The question as it was put:** `options` is history and only grows, so in principle a date can collect more than 64 distinct options over time. At the limit today, a decision is refused with a clear message (`OPTIONS_LIMIT`), and an import whose merged `options` would pass 64 fails as a whole with a schema error, leaving this device unchanged; no option is ever dropped. Neither failure can be removed without changing what a version-8 file may hold: either lift the count limit and rely on the existing per-record limit of 256 KiB (`MAX_ENVELOPE_BYTES`) with an explicit, tested check before each write and merge (the far, byte-based limit would still refuse a decision or count a merge as not applied when reached), or keep a count limit and accept that options past it are not kept. Version 8 is not released (`feat/stage-6`, not merged), so either could be made without a new `dataSchemaVersion`, but files with more than 64 options would then be refused by builds made before the change.

- The segment merge design above (T-227 to T-229), revised 2026-11-03 so that a device's later choice replaces its earlier one, has not had an independent review. On the owner's instruction of 2026-11-03 it is implemented on `feat/stage-6` with the tests listed in TESTING "Stage 6 test report"; the independent review (DEVELOPMENT, "Roles and collaboration") is still open and should happen before the branch is merged.

**Implementation choices (derived, recorded 2026-11-03 on `feat/stage-6`; not owner decisions; open to the same review):**

- **Status history:** `goals.statusHistory` lists `{ from, status, archived }` entries, written with each status or archive change, the last being the current state, so paused, archived, and completed periods are known to the consistency streak (T-185). A goal without it uses its current state for every day; the unknown past is not reconstructed. Completion leaves no current streak and keeps the longest.
- **Plan history shape:** `goals.planHistory` lists every plan with the date it took effect, the last being the current one. The first change of a goal without history also records the plan in effect since its start date; a change on the same local date replaces that day's entry.
- **Which goals get weekly plans:** a week's record is started only for a running goal (not archived or completed, inside its dates) with a deadline and selected workdays; a goal that already has a record for the current week gets an inactive segment when they are removed (T-213). A plan write after a change never writes a date that has more than one candidate; the owner decides it (T-223).
- **Estimate captures** are ordinary records the app never edits (not append-only), so two devices that captured different estimates for one occurrence give an ordinary conflict.
- **Compared plan:** any edit at or after the block's scheduled start keeps `comparisonPlan` if none is kept yet: a form edit, a drag, its Undo, a cancel, or a restore.
- **Dragging an actual session:** only an ended session, only after the owner confirms; start, end, and pauses move together, so its work time is unchanged, and a `times` correction keeps the times and pauses before and after, with an optional reason. New blocks are created only in the Planned subcolumn; the Actual subcolumn holds sessions.
- **Metric catalog:** `appUseStreak`, `workTime`, `plannedVsActual`, `completions`, `estimateAccuracy`, `outputRate`, `goalProgress`, `goalStreaks`. Window presets: today, the last 7, 30, or 90 days, this or last week, this or last month, and all time, plus a custom range. Each card has its own `id`. Suggested main layout: app-use streak, completed tasks, work time, planned versus actual, estimate accuracy, output rate. The main dashboard is written under its reserved ID at its first edit and shows the suggested layout until then; each edit applies to the stored dashboard in one transaction. The Reports page shows every catalog metric for one chosen window with the metric dictionary (T-197).
- **Import of weekly plans:** a plan already here that is newer or concurrent is its own preview category; with "Apply updates" the merged content is written with the merged version vector, raised for this device only when the content changed; a merge that meets the same device and counter with different content leaves the whole record unchanged and is counted as an integrity issue. New app-use dates are counted apart from other new records.
- **Timer details:** ending a work session from the timer (in the app or the floating window) asks for confirmation and ends it without outputs, which can be added afterwards on the Work screen (T-104, T-113); the task is never completed. The tone is a short Web Audio beep, whose audio context is created when the user starts a countdown.
- **Entries that cover one another (Codex review, 2026-11-04; data integrity, derived):** an entry can only cover one written before it, so a cycle of coverage within a date (A covered by B and B by A, or a longer loop) never comes from the app's own writes and merges; it is malformed data that schema validation alone does not catch. On import, a weekly plan record carrying such a cycle, or a merge that would create one, is a data-integrity issue: it is counted with the plans that have one, a new record is not imported, and an existing one is left unchanged, so this device's plan stays in effect. A date already stored with entries but no candidate (from before this check) is never shown as a silent "no data": it is marked as a data-integrity issue that needs the owner's decision, this device's own entry still applies while it has one (otherwise "no data" with the warning), automatic plan writes leave it to the owner, and the owner chooses among the segments of all its entries. The decision is written as usual (DECISIONS "Deciding a date"); only if malformed data claims that another entry has seen a higher `seq` of this device than its own does the new `seq` go past that claim, so the decision is not covered at once. A counter never passes the schema's maximum (`PLAN_SEQ_MAX`, 1,000,000,000): when this device's next `seq` for a date would, because its own counter or a malformed claim about it is already there, the goal view says that no choice can be recorded on this device and offers none, a decision is refused with nothing written (code `SEQ_LIMIT`), and an automatic plan write for that date is skipped so the recorded plan stays; another device, or importing a backup from before the issue, can settle it. When such a skipped write would have changed today's plan (the computed segment differs from the one in effect), the goal page warns that today's plan could not be recorded on this device and that the daily target still comes from the last recorded plan; with no difference there is no warning. The automatic write and the warning come from one pure function (`planWriteStep`), so they never disagree; nothing is rewritten, reset, or deleted, and the counter is not bypassed. Well-formed dates, conflicts (T-223, T-227), undecided dates (T-228), and decisions behave exactly as before.
- **Remaining workdays for the cap projection (Codex review, 2026-11-03):** "remaining workdays" in the maximum projected attainment are work opportunities as in T-185: selected workdays of the plan in effect, inside the goal's dates, while the goal is active and not archived. Days after today take the goal's current status, so a paused or archived goal adds no capacity until it is resumed or restored.
- **Per-record size of weekly plans (owner's choice of 2026-11-04; details derived):** `options` has no count limit.
